# 진행·경제 시뮬레이션 v0.1 — 2026-09-21

## 결론과 상태
**실행한 것은 경제 진행 모형이며 실제 이용자/엔진/전체 구조 콘텐츠 테스트가 아니다.**
기준 커밋은 `011e24081671ecf38a66e86b3bb348feb9b0e4a2`다.
센터/건물 비용과 수익, 숙련 성장, 오프라인 상한, 광고 보상을 넣어 7개 가정 시나리오를 실행했다.
기존 `economy_balance.json`, `progression.json`, `cats.json`, `buildings.json`은 이번 결과만으로 변경하지 않는다.
시골 마을 하나/고양이50/직원최대3/희귀도 없음/네 발 고양이/광고 포함 출시 원칙은 유지한다.

주요 발견은 세 가지다.
1. 하루2회 무광고 기준 모형상 축제 조건은 약33.0일. 전체 기간보다 **첫 수익 건물 가동까지 약48시간**이 더 중요한 문제다.
2. 초기 지원금만1,000→5,500G로 바꾼 실험에서는 첫 수입이 약24.5분, 축제 조건은약31.5일이었다. 초반과 후반을 함께 완화할 필요는 없었다.
3. 하루2회에서는 복귀 추가 보상만 쓰는 경우와 모든 보상형 광고를 선택하는 경우의 최종 모형 완료시점이 모두약22일이었다. 광고 종류를 많이 넣는 것과 각 보상의 가치가 큰 것은 다르다.

## 1. 입력 및 계산 범위
기준 GitHub JSON에서 다음 계산 필드를 읽어 로컬 입력으로 구성했다. 로컬 입력은 원본 전체 파일 복제가 아니라 **계산에 사용하는 필드의 투영**이다. 원본 데이터/아트 필드를 대체하지 않는다.
- cats: 고유ID, 기본5능력, 최소센터레벨.
- buildings: ID, 최대레벨, 해금센터레벨, 직원슬롯, 주/보조능력.
- progression: 정원, 주민/발전도/숙련조건, 축제 조건.
- development_score: 종류별 최고 완성레벨의 점수계수.
- economy_balance: 수익/비용/시간/직원효율/공급/경험치/광고/오프라인에 사용되는 계수.

수익은 건물 레벨·실제 배치된 주민 능력·해당 직업 숙련·공급 보너스로 계산한다.
공사는 실제 경과시간으로 끝나고, 기존 레벨은 완료 전까지 운영된다. 새 건물/새 직원 슬롯에 자동 배치하는 판단은 접속 중에만 한다.
기본 지원금2G/분, 오프라인 인정8시간, 소수 골드 유지, 직원0이면 영업수입0을 적용한다.
능력 경험은 주70%/보조30%, 능력상승 비용10×현재능력², 숙련은 기존 누적업무시간 곡선을 사용한다.
센터에 돌봄직원1마리를 우선 두고 현금수익시설을 채운다. 공방/진료소는 건설된 경우1마리. 기존 배치는 유지하여 경력이 누적되게 한다.
가구/관계 보너스는0, 꾸미기 소비/추가 주택 건설 비용은 계산하지 않는다.

## 2. 반드시 알아야 할 구조 대체 모형
`cats.json`의 `primaryCondition`은 아직 설명용 문자열이다. **50개 고유 발견조건, 날씨·생활이벤트·힌트를 실행했다고 주장하지 않는다.**
경제 영향만 분리하려고 최소센터레벨과 정원은 지키되, 탐색+돌봄을 직렬 타이머 하나로 대체했다.
센터1~10의 가정 시간(초): `60 / 120 / 300 / 600 / 1200 / 1800 / 3600 / 3600 / 5400 / 7200`.
새 작업 시작과 정착 수령은 접속 중에만 가능하다. 비접속 중 타이머는 진행되나 다음 고양이를 연속 자동 수령하지 않는다.
대상은 조건을 만족하는 미보유ID순. 중복 없음. CAT_050은 앞49마리가 있어야 시작한다. 구조 대기 중 고양이도 정원에 예약된다.
따라서 `collection50ProxyDay`와 `festivalProxyDay`는 **대체 구조 모형 아래의 수집/축제 조건 도달값**이다. 실제 출시판 완주 예측이나 엄밀한 최단시간 하한이 아니다.

## 3. 접속과 광고 가정
- 첫 접속30분, 이후1회10분.
- 하루2회는12시간 간격, 하루4회는6시간 간격.
- 최대90일까지 계산하되 모형 축제 조건 도달 시 종료한다. 종료 후 스냅샷은 만들지 않는다.
- 보상형 사용 시 복귀 추가 보상1회, 필요할 때10분 수익부스트 최대1회, 시간단축 최대1회/접속.
- 부스트 잔여가 충분하면 추가 광고를 보지 않는다. 시간단축은 유효 작업이 있을 때만 선택한다.
- 광고1회30초는 이 실험의 가정이며 실제 광고 길이가 아니다. 시청은 접속시간 안에 포함한다. 전부 정상 완료/보상 지급을 가정한다.
- 일일 광고 의무 횟수나 수익화 목표치를 제안하는 것이 아니다.
- 코드의 구매자는 센터 확장 가능 시 우선 확장하고, 새 수익시설, 부족 발전도의 비용효율, 제한된 회수기간 투자 순으로 판단한다. 인간 플레이나 전역 최적해가 아니다.

## 5. 첫 경제 체험 개선안 — 아직 미승인 실험
기본 지원금으로 센터2/3, 주택, 공원을 만들면 골드가 거의 남지 않는다. 다음 센터4 비용3,000G와 첫 생산시설 비용을2G/분 지원금으로 준비해야 한다.
이 과정 때문에 직접 돌봄과 첫 자동화는 빨리 보여도 마을의 생산·판매 체험이 늦게 열린다.
실험 `candidate_start5500_2_noads`는 **초기골드만5,500으로 덮어쓰고** 후반 비용/수익/정원/광고는 바꾸지 않았다.
첫 수입 약48시간→약24.5분, 전체 모형 종료약33.0일→약31.5일이었다.
제안: 첫30분 안에 구조→정착→자동화→첫 생산시설을 한 번 체험시키고 이후 축적 시간을 늘린다.
5,500G는 지급 방식이나 출시 확정값이 아니다. 튜토리얼 보상으로 분할할지 최초 지급으로 둘지는 다음 상세기획에서 결정한다.

## 6. 광고별 가치 검토
하루2회 전체 보상형 모형은 복귀44회+부스트36회+단축42회, 복귀만 모형은44회였다.
최종 대체구조 포함 완료는 모두약22일이지만 **중간 센터 해금·시설 조건 시점은 다르다.** 전체 광고가 언제나 무가치하다는 결론은 아니다.
이 접속 모형에서는 긴 오프라인 구간의 추가골드가 강하고, 짧은 온라인 부스트/10분단축의 효과가 최종 접속 시점 단위에 가려진다.
추론: 광고 슬롯 수를 늘리기보다 현재 세션에서 다음 건설/다음 구조를 실제로 경험하게 해주는 보상인지 확인해야 한다.
구조타이머를4배로 한 무광고 실험도 최종 시점이 같았다. 12시간 간격과 골드 대기가 큰 원인으로 보이지만, 다른 접속 패턴에서도 같다고 일반화하지 않는다.
광고단가/실사용자수/시청률을 모델링하지 않았으므로 광고매출은 계산하지 않았다.

## 8. 산출물과 재현
설정: `data/simulation_scenarios.json`.
결과요약: `reports/progression_simulation_v01.summary.json`.
실행기는 `tools/simulate_progression.py`, 단위테스트는 `tools/test_simulate_progression.py`를 사용했다.
**실행기 소스의 GitHub 업로드는 연결 도구에 의해 차단되어 이번 커밋에 포함하지 못했다. 실행기/테스트/로컬 계산 입력은 대화의 별도 ZIP에 제공한다.**
ZIP의 계산 입력은 원본 게임 데이터의 대체본이 아니므로 저장소 `data/`에 덮어쓰지 않는다.
도구 소스와 설정을 저장소에 적용한 환경에서는 다음 명령으로 계산을 재현한다.

```sh
python3 -S tools/test_simulate_progression.py
python3 -S tools/simulate_progression.py
python3 -S tools/simulate_progression.py --case base_2_noads --case base_4_ads --offline-step 1 --output reports/convergence_1min.json
```

전체 결과와 `.summary.json`이 생성된다. `--include-events`는 구매/센터/주민 이벤트 추적을 추가한다.
