# 저장·복구 계약 v0.1

상태: **구현 명세 + 참조모형 검사 / 게임 엔진 저장 구현 전**. 기준 커밋 `2464d168633429ec437c51f3722f2ff94a56052a`.
이번 문서는 기존 고양이50마리·건물13종·정원·비용·지원금·숙련곡선을 바꾸지 않는다.
기계판독 계약은 `data/persistence_contract.json`. SQLite는 Python 시험용이며 Unity/Godot 및 실제 저장 라이브러리를 선택했다는 뜻이 아니다.

## 1. 저장하는 것은 그림이 아니라 마을의 사실
| 묶음 | 영속 데이터 |
|---|---|
| 헤더 | saveId, schemaVersion, contentVersion, revision, 생성시각, 마지막 체크포인트와 시계 기준 |
| 골드 | 정수 미세단위 잔고(1G=1,000,000단위), 그 미만 계산 잔량, 지급·지출 고유ID |
| 고양이 | Resident ID↔Catalog ID, 지정이름, 구조기록, 성장능력/경험, 직업별 숙련/경력, 집, 친밀도/관계 |
| 건물 | 종류ID와 별도의 Instance ID, 완료레벨, 직원ID, 가구/주택 배정, 발전도 최고기록 |
| 진행작업 | 구조 예약 개체ID, 탐색·현장·돌봄 단계, 건설/제작 Job ID, 남은 작업량, 확정 비용·시간·버전 |
| 튜토리얼 | 완료 사실, 과거 직원배치, 최초영업, 실제 플레이시간, 지급한 지원ID |
| 정산·광고 | absenceId/settlementId, 기본 정산 영수증, 제안 보상, 시청시도, 지급한 rewardGrantId |
| 기타 | 축제 준비/첫완주, 설정, 저장 형식 마이그레이션 이력 |

월드의 GameObject/애니메이션 프레임/길찾기 경로/SDK 광고 객체는 저장하지 않는다. 재실행하면 실제 주민ID로 다시 표현한다.
화면 재생성으로 구조 고양이를 다시 생성하지 않는다. 예약 단계부터 Resident ID를 정하고 정착까지 유지한다.
한 마리의 근무지는 하나, 직원 최대3, 정원은 정착+진행구조 한 칸이며 최대50. 외출 연출은 배치를 지우지 않는다.

## 2. 하나의 변경을 쪼개 저장하지 않는다
아래는 각각 단일 영속 트랜잭션이다.
- 건설비 차감 + Job 생성.
- 고양이 구조 예약 + 정원 점유.
- 정착 시 예약 해제 + 동일 Resident 생성 + 도감 기록.
- 지원금 증가 + 해당 지원ID 지급 기록.
- 오프라인 기본수익 + 정산 영수증 + 시간 커서 갱신.
- 광고 보상 적용 + 지급키 기록.
- 공사 완료 + 완료레벨/해금 갱신.
- 첫 축제 완료 + 일회성 지급이 있다면 해당 기록.

단일 명령 처리기가 변경을 직렬화한다. commandId가 같고 내용이 같으면 재처리는 no-op, 내용이 다르면 오류다.
예전 revision을 기반으로 온 UI 명령은 최신 상태로 다시 확인한다. 오래된 스냅샷으로 새 저장을 덮지 않는다.
**영속 저장 성공 후에만 완료 UI를 확정**한다. 실패하면 건설·보상이 됐다고 표시하지 않고 재시도 안내한다.

## 3. 저장 시점
고양이 정착, 건설 결제, 직원/집 변경, 지원금, 정산, 광고시도 생성/획득증거/지급, 주요 진행은 즉시 저장 대상이다.
연속 수익·숙련·생활 기록은 최대5초 간격 체크포인트를 초기 목표로 하고 중요 명령 전에 누적분을 반영한다.
일시정지/백그라운드 콜백에서도 저장하지만 종료 콜백만 믿지 않는다. Unity 공식 문서도 모바일에서 종료 이벤트가 보장되지 않는 경우를 설명한다.
출처: https://docs.unity3d.com/ScriptReference/MonoBehaviour.OnApplicationQuit.html (확인 2026-09-21).

정상 체크포인트 사이의 비핵심 생활기록 일부는 장애 시 이전 상태로 돌아갈 수 있다. 모든 강제종료에서 0손실이라고 약속하지 않는다.

## 4. 저장 포맷과 백업
엔진 어댑터는 트랜잭션 DB 또는 검증한 임시파일→원자적 교체/저널 방식 중 실기기에서 확인한 방식을 사용한다.
단순히 JSON 파일에 순차 덮어쓰기만 하지 않는다. flush/교체/디렉터리 내구성은 플랫폼별로 검사한다.
최근 정상 커밋의 백업2개를 유지하는 안이며, 백업은 검증된 커밋에서만 생성한다. SQLite 채택 시 실행 중 DB 파일만 복사하지 말고 해당 백업 절차를 구현한다.
체크섬은 우발 손상 탐지용이지 해킹 방지 서명이 아니다.

읽기 실패 시 원본을 보존하고 검증된 백업의 saveId/revision/시각/형식을 검사한다. 복구 상태와 시각을 알려주고 확인한다.
원본과 백업 모두 불량이면 오류 화면/내보내기/새게임 명시확인으로 처리한다. **조용히 새게임으로 초기화하지 않는다.**
구버전 앱이 더 새 저장형식을 만나면 업그레이드를 안내하며 쓰기를 거부한다.

## 5. 버전 변경
저장 스키마 버전, 콘텐츠 버전, 밸런스 버전을 분리한다. 이전 저장 복사본에 migration을 실행하고 ID/정원/지갑을 검증한 뒤 교체한다.
실행 중인 유료 작업은 결제 당시 확정 비용/작업량/보상제안을 보존한다. 재접속했다고 재결제하지 않는다.
새 기본능력으로 성장치를 덮어쓰지 않는다. 미등록 콘텐츠ID는 임의 대체 고양이가 아니라 보존·격리하여 오류를 알린다.
주요 마이그레이션/백업 복구는 이번 참고 코드의 구현 범위 밖이며 출시 전 fixture·실기기 테스트가 필요하다.

## 6. 로컬 저장의 경계
v1 설계는 단일기기 로컬 진행을 기본으로 삼지만 앱 삭제/기기 교체/파일 전체 손실 복구가 구현됐다는 뜻은 아니다.
클라우드나 저장 내보내기 UX/계정 선택은 별도 결정이다. 로그인 없이 플레이 가능하게 두고 광고 영수증 서버와 클라우드 저장을 혼동하지 않는다.
중복 방지는 **같은 saveId의 보존된 원장 계보 안**에서 성립한다. 사용자가 오래된 파일을 복원하거나 앱 데이터를 지운 경우까지 로컬만으로 전역 exactly-once를 보장하지 않는다.
금전 관련 지급키는 관련 영수증이 살아 있는 동안 임의 삭제하지 않는다. UI 알림 삭제와 지급 원장 삭제를 분리한다.

## 7. 인수 기준
저장 직전/직후 중단, 중복 명령, 연속 두 번 탭, 다른 콜백 순서, 잘못된 버전, 디스크 공간 부족, 손상파일·백업, 앱 업데이트를 시험한다.
자동 스크립트만 통과해서 출시하지 않는다. SQLite 트랜잭션의 일반 근거는 https://www.sqlite.org/atomiccommit.html 이며, 사용하는 파일시스템과 어댑터의 실제 동작은 별도 확인한다.
